# Example — `hydra-invoice-split` (Phase 1: proof on real billing code)

The one-slice proof that the spec-driven-dev loop works on **real Hydra billing
code**, not just a toy grammar. Target: two pure functions lifted from
`billing-system/packages/hydra-internal/src/helpers.ts` —

- `roundFloatToCents(float, algorithm?)` — round a float to a cents-valid number.
- `evenlySplitWithCorrection(total, count)` — split an invoice total into `count`
  cents-valid parts that sum **exactly** to the total (penny remainder to the tail).

Chosen because they are genuinely pure (no DB/HTTP/async/Date), have **zero
external dependencies** (run under plain Node), do real billing math, and are
directly tested in Hydra — so fixtures could be lifted from real tests.

## Why this is a real test (and not the money-cart toy)

The money-cart generator renders a closed value grammar and cannot express this
code (it needs `Math.round/ceil/floor`, `abs`, array `map`/`reduce`, a ternary).
So this module has **no `spec-codegen` block** — it is generated by the **LLM
generation path** (for Phase 1, by Claude acting as the generator, from the spec
alone). The spec is the source of truth:

- `spec/standards/conventions.md` — S3 (cents-rounding) and S4 (correction distribution)
- `spec/contracts/invoice-split.contract.md` — real TS signatures + guarantees
- `spec/modules/invoice-split/` — `spec.md`, `constants.md`, `fixtures/`
- `reference/invoice-split.reference.ts` — the verbatim Hydra code, used ONLY as the behavioural oracle
- `generated/invoice-split.ts` — the implementation produced from the spec (arithmetic, deliberately structured unlike the reference)

## The proof (reproduce)

From `skills/scrutinize-spec/`:

```
node scripts/score.js examples/hydra-invoice-split/.analysis/invoice-split.json
node examples/hydra-invoice-split/tools/verify.js
node examples/hydra-invoice-split/tools/behavioral-diff.js
```

Results:

| Check | Result |
|---|---|
| **Scrutinize score** (document mode) | **89.4**, `cappedBy: []` — no gate binds (88.8 before adding the assumptions section on a refine pass) |
| **Fixtures** (exact + property) | **18/18 pass** against the spec-generated code |
| **Behavioral diff** vs Hydra reference | **242,912 comparisons, ZERO divergences** (floats −50.05…50.05 × {nearest,up,down}; splits 0…200 × 9 counts; negative totals) |

The generated code passes fixtures **and** matches the real Hydra function
bit-for-bit across a dense sweep — while being written from the spec, not copied
from the source. That is the actual proof that a precise spec regenerates
correct, behaviourally-identical billing code.

## Phase 2 — the automated CLI generation (blind, fixtures withheld)

`generated/invoice-split.ts` is now produced by the **automated LLM path**, not
hand-authored. `tools/sdd-generate.js` assembles a prompt from the spec —
standards + contract + constants + module `spec.md`, **with the fixtures
withheld** — pipes it to the `claude` CLI, and accepts the result **iff every
fixture passes** (validity is behavioural, not byte-identity). Reproduce from
`skills/scrutinize-spec/`:

```
node tools/sdd-generate.js examples/hydra-invoice-split --module invoice-split --model claude-sonnet-4-5
node examples/hydra-invoice-split/tools/verify.js
node examples/hydra-invoice-split/tools/behavioral-diff.js
node tools/sdd-check.js examples/hydra-invoice-split
```

| Check | Result |
|---|---|
| Generation | claude CLI, fixtures withheld, **passed on attempt 1** |
| Code identity | **64 lines different** from the Phase 1 hand-generation — so fixtures-pass validity (not byte-hash) is doing the real work |
| Fixtures | **18/18 pass** |
| Behavioral diff vs verbatim Hydra reference | **242,912 comparisons, ZERO divergences** |
| Drift (`sdd-check`) | in sync (STALE on spec edit, INVALID on broken artifact, ORPHAN on stray file) |

The generator saw the spec but **not** the fixtures or the reference, and still
reproduced the real Hydra billing math bit-for-bit across the sweep. That is the
blind test Phase 1 deferred.

The gate runs the same way: `node tools/sdd-build.js examples/hydra-invoice-split
--min-score 95` **refuses** (the spec scores 89.4), and at `--min-score 85` it
clears and generates — the scrutinize score is a live precondition, not a
decoration.

## Honest limits of this proof

- **Property fixtures matter.** The real Hydra tests are property-based
  (sum-preservation, length, bounds, cents-validity), so `verify.js` here supports
  `properties`, not just exact `expect`. Writing the spec surfaced that the
  original tests under-pin the exact penny distribution; the fixtures here add
  exact-array cases the originals lacked.
- **One pure function pair.** Entities, routers, and DB-touching code need richer
  contracts and a real fixture harness (supertest / test DB) — Phase 3.
