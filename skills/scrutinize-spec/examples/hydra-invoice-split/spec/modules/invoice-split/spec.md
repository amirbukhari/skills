# Module — `invoice-split`

Real billing math lifted from Hydra (`packages/hydra-internal/src/helpers.ts`):
round a float to cents, and split an invoice total into N cents-valid parts that
sum exactly to the total. Pure, zero external dependencies.

**This module has no `spec-codegen` block.** Its behaviour is not expressible in
the money-cart template grammar (it needs `Math.round/ceil/floor`, `Math.abs`,
array `map`/`reduce`, and a ternary). It is therefore generated by the **LLM
generation path**, not the deterministic template renderer — this is exactly the
surface Phase 1 exists to prove. The behavioural source of truth is:

- `standards/conventions.md` — S3 (cents-rounding) and S4 (correction distribution)
- `contracts/invoice-split.contract.md` — the TypeScript signatures + guarantees
- `constants.md` — the literal values (`CENTS_DECIMALS`, `CORRECTION_UNIT`, `ROUND_EPSILON`)
- `fixtures/` — executable input→expected and input→property cases

## Functions

- `roundFloatToCents(float, algorithm='nearest')` — S3.
- `evenlySplitWithCorrection(total, count)` — S4; depends on `roundFloatToCents`.

## Acceptance

The generated implementation is valid iff every fixture in `fixtures/` passes
(exact `expect` and every `property`). Beyond the fixtures, `tools/behavioral-diff.js`
sweeps a wide range of `(total, count)` inputs and compares the generated output
elementwise against the verbatim Hydra reference — the real proof that the spec,
not the original source, drove a behaviourally-matching implementation.

## Assumptions

- **Valid input** — callers pass a finite `total: number` and an integer
  `count >= 1`. Invalid input (`count <= 0`, `NaN`/`Infinity` total) is out of
  scope (contract "Error / edge behavior"); the Hydra reference does not guard it
  and neither does the generated code.
- **Float dollars, not integer cents** — amounts are JS `number` dollars (S1).
  The `ROUND_EPSILON` correction (S3) is what makes this safe against IEEE-754
  representation error; it is assumed sufficient for the amount magnitudes real
  invoices use (sub-billion dollars), matching the reference's own assumption.
- **Execution** — the generated `.ts` runs under Node's native type-stripping
  (Node ≥ 23) or any TS toolchain; it uses only `Math`, arrays, and arithmetic,
  no external packages.
- **Rounding policy is half-up by magnitude** — chosen to match the existing
  Hydra behaviour, not re-litigated here; if billing policy ever required
  half-even, that is a spec change (S3), which would regenerate the code.
