# Generators

Everything in this folder is hand-written: edit it directly, then run `__PM_RUN__ generate`. What generation writes
lives outside this folder, and every such file starts with a "Generated by" line naming the command that writes it.
Review the declarations and the generators, not their output.

- `resource.ts` and `manifest.ts` define the declaration formats. Keep the formats in code, not in prose.
- `resources/` holds one declaration per resource. A resource belongs to no feature: its endpoints are always mounted.
- `manifests/` holds one declaration per feature: the resources it uses, by operation, and the actions it owns.
- `scripts/` holds the generators. Each generator's `command.ts` entry point sits beside it.

## What each part generates

| Declaration part | Generates |
|---|---|
| resource `fields` | The contract: record, input and filter zod schemas with their types, and one schema per enum field. |
| resource `fields` with `unique` | The store's lookup by that field and the service's conflict check (409). |
| resource `fields` of type `reference` | The service's check that the referenced record exists (400). |
| resource `operations` | The endpoints the router opens. The service and store always hold every operation, for server code to call. |
| manifest `actions` | The action contract, `action.ts` (rewritten every run), a typed `handler.ts` stub (written once) and the registry. |
| manifest `resources` | Checked against the declarations: a feature may select only operations the resource declares. |

Every resource also gets `created` and `modified`, which no declaration names; the loader adds them.

## Adding a resource

1. Copy an existing file in `resources/` to `resources/<name>.ts`. The file name is the resource's `name`: kebab-case,
   plural.
2. Declare its `fields` and `operations`. A field a list filters by is a string, an enum or a reference.
3. Add the name to the pinned list in `scripts/declarations/resources/load.test.ts`. Adding a resource is a decision
   made there, in the same change.
4. Name it in a manifest's `resources`, with the operations that feature uses.
5. Run `__PM_RUN__ generate`, then `__PM_RUN__ test` and `__PM_RUN__ typecheck`.
6. Add a test under `__API_DIR__/generated-code-tests/` for any rule the declaration states that the existing tests
   do not already cover.

Nothing else is written by hand: the endpoints, validation, conflict checks and types come from the declaration.

## Adding an action

An action is behaviour a plain create or update cannot express. Declare it in its feature's manifest with its
`input` and `output` fields, run `__PM_RUN__ generate`, and fill in the `handler.ts` stub generation left under
`__API_DIR__/features/<key>/actions/<action-name>/`. Typecheck holds the handler to its declared input and output;
the runtime validates both on every call. Commit the regenerated `actions/index.ts`, `action.ts` and action contract:
`__PM_RUN__ check:generated` fails in CI when they drift from the manifests.

## Changing what is generated

Change a renderer under `scripts/`, never its output. Each renderer is a pure function from declarations to text, with
a test beside it. The store renderer is the seam for a real datastore: it writes an in-memory store behind the
`IStore` interface, and the service depends only on that interface.

## Rules that keep this style working

- Declarations are plain data. They import types and shared value sets, never application code.
- A generated file is never edited; a hand-written file is never overwritten. Generation seeds `handler.ts` once and
  leaves it alone afterwards.
- A wholly generated folder is generated in full: files a declaration no longer produces are deleted.
- Gitignored output is regenerated before tests and typecheck. Committed output has a `--check` mode.
- A new field type is added in four places together: `resource.ts`, the declaration schema, `shared/zod.ts`, and a
  test.
